# 06 — UI System (C++ `src/liblt/UI`, `Game/Widget`, LTSL `Widget/*`)

Scope: the retained widget framework in `src/liblt/UI/` (plus a little of `src/liblt/Game/`), and all LTSL UI code: `resource/script/Widget/**`, `Widgets.lts`, `Colors.lts`, `Fonts.lts`, `Icons.lts`, `Icon/Cursors.lts`, `App/widget.lts`.
I got everything here by reading the code. I did not run the game. Where I am inferring or unsure, the text says so (**[unverified]**).

---

## 1. Overview

- **One framework, one widget tree.** The C++ side is small (~3.1k lines). It has a generic `WidgetT` node that holds a list of **components** (decorators) and a list of **children**. It also has a two-pass layout, a focus-capture pass, message passing (`Send`/`SendUp`/`SendDown`), batched SDF-style **glyph** primitives, panels, text, textures, offscreen **Layer** render targets with a post-process **Compositor**, and `Rendered` widgets that embed a full 3D render pipeline.
- **Nearly all UI behaviour is written in LTSL.** The C++ `Widget_Custom` component binds an LTSL type's methods (`CreateChildren`, `PreDraw`, `PostUpdate`, `Receive`, …) as hooks. LTSL then builds a library of ~25 decorator components (Align/Expand/Margin/Padding/Capture*/Clickable/Tooltip/Focus*…). On top of those sit ~20 basic widgets (Text, Button, Tab, Slider, TextField, ScrollFrame, Window, Browser, RadialList…) and the game screens: HUD, reticle, minimap, mini-scanner, scanner, system map, object info, assets, cargo, market + transactions, observatory, plus dev tools (DevPanel, ModelEditor, TextEditor, ImageEditor, FontPreview).
- **Visual identity.** Additive HDR glyph lines/arcs, bevelled translucent panels with soft shadows, and a scanline/noise "hologram" compositor. The palette is cyan `Colors:Primary` with orange `Colors:Secondary` highlights, using the Rajdhani/Iceland fonts. It is distinctive and fully procedural: no texture atlases, and every icon is built from vector glyphs.
- **The "two generations" are really two *hosting* styles of the same framework.** Both create `Interface_Create "UI"` and add widgets to it. The older style (war/dogfight/rails) draws the UI *inside* the 3D view as a render pass (`RenderPass_Interface`). The newer style (`App/widget.lts`) makes the whole app a widget tree in which the 3D view is just a `Widget_Rendered` child. `src/old/launcher/launcher.cpp` does use a genuinely older, different API (`Widget*`, `CreateUIGroupY`, `CreateUIDropDown`) that no longer exists in liblt.
- **Maturity.** The framework is complete and usable. The HUD, object info, assets, cargo and market are the most finished screens. Many tabs and menu items are placeholders. The game menu buttons do nothing. There is no settings screen in practice, no docking/station UI, no star map, no fitting or industry screens, and no save/load UI.

## 2. Architecture

### 2.1 The widget node and the component (decorator) model

```
WidgetT (C++, RefCounted)                 WidgetComponentT (C++, virtual hooks)
 ├─ components : Vector<WidgetComponent>   ├─ CreateChildren(out Vector<Widget>)
 ├─ children   : Vector<Widget>            ├─ GetHash / GetName / GetPadding / IsAlive
 ├─ parent     : Pointer<WidgetT>          ├─ Create / Destroy
 ├─ pos,size,minSize,maxSize,greed (V2)    ├─ PrePosition / PostPosition      (layout)
 ├─ color, alpha                           ├─ PreUpdate / CaptureFocus / PostUpdate
 ├─ focusKey/focusMouse/focusScroll        ├─ PreDraw / PostDraw
 └─ flags: deleted, initialized, rebuild   └─ Receive(Data)                   (messages)
```

- A **widget is one node**. In LTSL, `Components:Expand (Components:Padding … (Stack (Custom Widget Foo)))` does **not** create nested nodes. Each call *adds a component to the same `Widget`* and returns it. Components are added innermost-first: `[Foo, Stack, Padding, Expand]`.
- Hook order is symmetric, like decorators:

| Phase | Component order | Notes |
|---|---|---|
| `PrePosition` | forward (inner → outer) | runs after children's PrePosition (bottom-up) |
| `PostPosition` | reverse (outer → inner) | runs before children's PostPosition (top-down) |
| `PreUpdate` | forward | before children update |
| `CaptureFocus` | forward | after children update |
| `PostUpdate` | reverse | focus flags are final here |
| `PreDraw` | reverse (outer first) | before children draw |
| `PostDraw` | forward | after children draw |
| `Receive` | forward | via `Send` |

- **`Widget_Custom(widget, data)`** (`UI/Widget/Custom.cpp`) is the bridge to scripts. It looks up methods by name on the LTSL type (`CaptureFocus, Create, CreateChildren, Destroy, GetHash, GetName, GetPadding, PostDraw, PostPosition, PostUpdate, PreDraw, PrePosition, PreUpdate, Receive`) and calls them with `(instance, self)`. Missing methods are skipped. The LTSL alias is `Custom`.
- **Children** come from three sources:
  1. `CreateChildren`. It is called once when the widget is uninitialized, and again after `Rebuild` (clear and recreate on the next PrePosition).
  2. Explicit `AddChild` / `RemoveChild`.
  3. `Dynamic`. Every `PreUpdate`, the `CreateChildren` list is regenerated and reconciled against the existing children by `GetHash`. New hashes are added and missing ones are cleared. This is a React-style keyed diff, used for lists that track world state (log, targets, sockets, world-object brackets, map, market list).
- **Rebuild-as-state-change** is the dominant idiom. Widgets rebuild their children when focus or selection changes (`FocusRebuild`, `Button`, `Tab`, `Element`). Some rebuild *every frame* (`HUD/Container`, `DevPanel/Clock`, `Status`, `Performance`, `Market/Transaction:Details`). Rebuilding every frame works, but it is effectively immediate mode, paid for with allocations.
- **Deletion.** `Widget.Delete` sets `deleted`. The parent removes the widget during its next `PrePosition`, and `Interface` removes top-level widgets in `Update`.

### 2.2 Frame loop (Interface)

`InterfaceImpl` (`UI/Interface.cpp`) holds a flat list of root widgets.

```
Interface.Update():
  Cursor_Push(mouse), ClipRegion_Push(0, window)
  for root in reverse(widgets):            # topmost (last added) first
     remove if deleted
     root.PrePosition()                    # bottom-up: minSize
     root.pos=0; root.size=root.maxSize=window
     root.PostPosition()                   # top-down: pos/size/maxSize; clears focus flags
     root.Update(state)                    # PreUpdate → children (reverse) → CaptureFocus → PostUpdate
Interface.Draw():
  Cursor_Push, ClipRegion_Push
  for root in widgets: root.Draw()         # PreDraw → children (forward) → PostDraw
```

Layout and update happen in the same call. Draw is separate. Drawing does **not** flush the glyph batch at the end; `ClipRegion_Pop` and Layer/next-draw calls flush it.

### 2.3 Layout

The layout is a two-pass constraint system, similar to a simplified flexbox.

| Pass | Direction | What happens |
|---|---|---|
| PrePosition | bottom-up | Node resets `pos=GetPosDefault(0)`, `minSize=0`, `greed=0`. Children run first. Components then grow `minSize` (Text: text extent; MinSize; Margin adds; List sums children; Stack takes the max). Finally `size = minSize`. |
| PostPosition | top-down | The parent receives `pos/size/maxSize`. Its components (outer first) adjust them (Margin shrinks, Expand mixes `minSize→maxSize`, Align offsets by `(maxSize-size)*scale`, MaxSize clamps). Container components then place the children (`child.pos += origin`, set `child.maxSize`). Then each child runs its own PostPosition. |

| Layout primitive | Where | Behaviour |
|---|---|---|
| `Stack` (C++) | `UI/Widget/Stack.cpp` | All children overlap in the padded content box. Each child's `maxSize` = the content box. |
| `ListH spacing` / `ListV spacing` (C++) | `UI/Widget/List.cpp` | Sequential placement with spacing. The cross-axis `maxSize` = inner size. Leftover space on the main axis is distributed to children by `greed` (flex-grow). |
| `Layer`, `Rendered` | C++ | Force `size = maxSize` (fill the parent). |
| `Components:Expand / ExpandX / ExpandY / ExpandCustom f` | LTSL | `size = Mix(minSize, maxSize, f)`, i.e. fill the available space. |
| `Components:Greedy / GreedyX / GreedyY` | LTSL | Set `greed`. Used with ListH/V to take the remaining space. `Widgets:EmptySpaceH/V` = greedy expanding spacer. |
| `Components:Align* (9 presets + Align v)` | LTSL | Place inside the slot: `pos += (maxSize-size)*v`. |
| `Components:Margin inner outer` | LTSL | Adds to `minSize`, shrinks `size/maxSize`, offsets `pos` by `inner`. Note that the "outer" margin does not offset. |
| `Components:Padding inner outer` | LTSL | Returns `GetPadding` = (left, top, right, bottom), which Stack/List consume. |
| `Components:MinSize / MaxSize` | LTSL | Clamp. |
| `Components:Positioned p` / `Draggable` | LTSL | Absolute offsets in PrePosition. Draggable snaps to 32 px on release. Positioned responds to `MessageSetPos`. |
| `Widgets:Grid`, `GridList`, `HUD/Sockets` hex packing, `RadialList` | LTSL | Custom placement in `PostPosition`. |
| `Widgets:ScrollFrameV` | LTSL | Hides the content's `minSize.y`, offsets children by `scroll`, clips, draws a scrollbar. Supports PgUp/PgDn/Home/End and the wheel. `ScrollFrameH` is an **empty type** (unimplemented). |
| `Widgets:ListH1..6 / ListV1..5 / Stack1..5 / Pair` | LTSL | Convenience builders. They exist because LTSL lacks varargs. |

### 2.4 Input, focus and routing

- **Cursor stack** (`UI/Cursor.cpp`): `Cursor_Get/GetLast/GetDelta/Push/Pop`. `Layer` pushes a *projected* cursor: it ray-casts the screen point onto the layer's surface mesh and takes the UV. That makes UI on curved or 3D surfaces hit-testable.
- **Clip stack** (`UI/ClipRegion.cpp`): intersecting scissor rectangles, plus `ClipRegion_GetMin/Max` for hit tests. `PushNoClip` is for tooltips.
- **Focus** comes in three independent channels: `Key`, `Mouse`, `Scroll`.
  1. `PostPosition` clears every node's flags.
  2. During `Update`, children update first, in **reverse** order (topmost first). Then `CaptureFocus` runs: `Components:CaptureKey/CaptureMouse/CaptureScroll` set the flag if the cursor is inside the rect, intersected with the clip.
  3. A shared `WidgetUpdateState` records whether a channel has already been claimed. If a child or a later sibling claimed it, this node's flag is forced false.
  4. Result: **the deepest, topmost widget wins** each channel. Ancestors can ask `HasFocusMouseRecursive`.
- The flags are only meaningful in `PostUpdate` and the following draw. Scripts read `self.focusMouse` there, and they read the mouse/keyboard *globals* directly (`Mouse_LeftPressed`, `Key_Escape.Pressed`, `Keyboard_ModifyString`). There is no event queue and no keyboard-focus traversal (Tab order). **Keyboard focus = cursor hover** for `CaptureKey`. `TextField` keeps its own sticky `focus` bool.
- `Handling.lts` sets its own flags to true in PostUpdate. This is a self-flag hack that does not block other widgets.

### 2.5 Message passing

- `Data` messages: any LTSL type instance, tested with `data.IsType "Name"` and `cast`.
- `Send` delivers to this node's components. `SendUp` delivers to each ancestor in turn up to the root. `SendDown` reaches all descendants recursively. `SendSiblings` reaches the siblings.
- **Common patterns:**

| Pattern | Example |
|---|---|
| Button → ancestor command | `Button:Create (MessageBuy item) "BUY"` sends `onPress` up. `MarketFrame.Receive` opens `Transaction`. |
| Request/response query ("pull" via a mutable message) | `Messages:GetLabel w "quantity"` sends `MessageGetLabel` up/self, and the owner (Slider, Tab) fills in `contents`. `Messages:GetObject` does the same downward. |
| Root-level window spawning | `self.SendUp (Messages:MessageAddWidget w)`. `HUD.HUDLayer`, or the app root in `map.lts`/`market.lts`, adds it centred with a margin. `MessageAddContextMenu` works the same way for radial menus. |
| Factory via message, to break circular module imports | `Messages:CreateObjectInfo`. Sub-panels send it up, and `ObjectInfo.Receive` fills `msg.widget`. The code comments call this "hackery" and mention "2-pass compile" limits of LTSL. |
| Group selection | `Tab:TabSelect group label` goes up. The parent `SendDown`s it, and the other tabs in the group deselect. |
| Broadcast refresh | `Messages:MessageRefresh` after a market transaction. |
| Browser navigation | `MessageLink widget` pushes onto the `Browser` history stack. Back/forward use icon buttons. |

### 2.6 Rendering

All 2D rendering goes through `WidgetRenderer` (`UI/WidgetRenderer.cpp`), a static batcher.

| Primitive | API | Implementation |
|---|---|---|
| **Glyphs** | `Draw glyph center scale color alpha` (`Glyph_Draw`) | Each glyph type is one expanded quad with its own fragment shader (`resource/shader/fragment/ui/{arc,box,circle,gradient,grid,line,linefade,rect,ring,triangle}.jsl`), drawn as SDF-like analytic shapes. They are queued per glyph type and **flushed as one draw per type**. **The flush uses additive blending**, which is why everything glows and why colours above 1 (`2.0 * Colors:Primary`) are common. Glyph types: `Arc, Box, Circle, Line, LineFade, Gradient, Grid, Rect, Ring, Triangle`. |
| **Icons** | `Icon` = list of glyphs; `icon += glyph`, `Draw icon center scale color alpha` | Vector icons in unit space, scaled at draw time. |
| **Panels** | `DrawPanel pos size color innerAlpha alpha bevel`, `DrawPanelRadial pos r1 r2 phase angle color innerAlpha alpha bevel` | Alpha-blended quad with a 32 px shadow margin (`ui/panel.jsl`, `ui/radialpanel.jsl`). Flushes the glyph batch first. |
| **Text** | `DrawText / DrawTextGlow font text pos size color alpha centered`, `GetTextSize` | Delegates to `LTE/Font` (another cataloger's area). Flushes before and after. The glow variant is additive. |
| **Textures** | `Draw texture pos size alpha`, `DrawAdditive …` | Simple quad. |
| **3D hologram** | `DrawRenderable renderable transform camPos camLook camUp fov pos size color alpha time` (`WidgetRenderer/DrawRenderable.cpp`) | Renders any `Renderable` into a sub-viewport with a `HoloStyle` render style (`hologram.jsl`, additive). Used for ship previews. |
| **Layer** | `Layer compositor surfaceMesh resolution widget` (`UI/Widget/Layer.cpp`) | Renders the subtree to an RGBA16F offscreen buffer, then `compositor.Composite(buffer, surface)` draws it onto a mesh (usually `Mesh_Quad`). Supports the projected cursor. |
| **Compositors** | `Compositor_None`, `Compositor_Basic noise lines gradeBlue`, `Compositor_Custom base data` | None = plain blit (`ui/none.jsl`). Basic = the "hologram" look with scanlines, noise, a blue grade and age-based animation (`ui/basic.jsl`). Custom = an LTSL `Composite(texture) → texture` pre-pass feeding a base compositor. **`Compositor_Custom` is unused by scripts.** |
| **Rendered** | `Widget_Rendered passes` (`UI/Widget/Rendered.cpp`) | Runs a full `RenderPass` chain (clear, camera, SMAA, post…) into the widget's own 3 colour + 2 small buffers + depth, then presents the result as a quad. This is how the 3D game view becomes "just a widget". |
| **RenderPass_Interface** | `RenderPass_Interface ui` | Older hosting style. Inside a render pipeline, it draws the Interface to the tertiary buffer and composites it over the frame (`ui/composite.jsl`) **before** later post passes (e.g. dither). |

### 2.8 Old Interface hosting vs new widget-app hosting

```
OLD (war.lts, dogfight.lts, rails.lts)            NEW (App/widget.lts; ltheory, handling, hud, ui, market…)
App (plain type, Main returns it)                 Main returns widget:Create <rootWidget>
 ├─ ui       = Interface_Create "UI"               App (widget.lts)
 │    └─ Widget/HUD:Create player                   └─ ui = Interface_Create "UI"
 └─ gameView = Interface_Create "Game View"              ├─ rootWidget (e.g. Stack(Custom Widget App))
      └─ Widget_Rendered [Clear, Camera, SMAA,           │    ├─ Widget_Rendered [Clear, Camera, SMAA, Dither]
            RenderPass_Interface ui, Dither]             │    └─ Widget/HUD:Create player
Update: ui.Update; gameView.Update; gameView.Draw        └─ (Ctrl+Tab) Layer(Compositor_Basic, DevPanel)
 (ui is drawn by the render pass, so it gets        Update: hotkeys; ui.Update; ui.Draw
  dithered with the frame)
```

`App/widget.lts` hotkeys: **Ctrl+Tab** toggles a DevPanel "desktop" layer and **T** runs `Shader_RecompileAll`. A commented-out **F4** Settings layer remains in the file. A custom `HUDApp` can also be the root with an `Interface` of its own (`map.lts`, `market.lts` create their own `Interface` and handle `MessageAddWidget` themselves).

## 8. Assessment for the two goals

### 8a. Pushing toward a playable game (EVE-like single-player)

**Framework adequacy: yes, with caveats.**

| Aspect | Verdict |
|---|---|
| Layout | Good enough: stack/list/flex-grow/align/margin/padding/scroll. It lacks tables/columns (rows fake columns with `MinSize`), wrapping text and horizontal scroll. |
| Input | Adequate for mouse-driven play. Weak for text entry and keyboard navigation. There is no drag-and-drop between widgets (needed for inventory and fitting), though `Draggable` and messages make it buildable. |
| Windows | `Window`, `FocusWindow`, `Browser`, `HUDWidget` (move/resize) and context menus exist. There is no window manager (z-order on click, persistence, stacking/tabbing like EVE). |
| Rendering | Distinctive and cheap. The additive-only glyphs constrain some designs. |
| Productivity | Hot-reloadable scripts and T shader reload make iteration fast. LTSL's single-pass compile causes awkward workarounds. |

**Screens for a playable loop** (fly, fight, loot, trade, upgrade):

| Loop step | Have | Missing |
|---|---|---|
| Fly / navigate | HUD, reticle, minimap, system map, flight control | Overview list, selected-item actions (approach/orbit/warp/dock), star map/route, autopilot UI |
| Fight | Targets, lead markers, integrity, brackets, radial Target | Capacitor/shield/armor display, module activation/fire groups, lock timers, damage feedback/log |
| Loot / cargo | Cargo list, item info | Loot/jettison/transfer windows, drag-drop |
| Trade | Market browse + buy/sell transaction | Your own orders, history, station-scoped market, hangar to move goods |
| Upgrade / fit | — | Fitting window, ship hangar, repair |
| Progress | Assets, wallet readout | Skills/character, missions/agents, industry |
| Meta | Esc menu shell | Working save/load/settings/keybinding screens (the C++ `Widget_Settings` + `Settings_Button` rebinding exists and could be wired), main menu/splash (the `SplashScreen` exists, dead) |

Roughly: **the HUD, Show-Info, Assets and Market are 60–80% of what a prototype needs. Fitting, docking/station, overview, missions and settings are 0%.** Building them in LTSL on this framework is straightforward. The Market and Assets code is the template to copy: `Dynamic` lists, selection via pointers, a preview pane, modal transactions.

**Cheap wins:** wire `GameMenu` buttons; re-enable the WorldObject Info/Owner actions (fix why they were disabled); surface `Widget_Settings`; make fire groups real; turn WorldObjects into a sortable Overview list; persist HUD layout; fix the T and Tab key conflicts.

### 8b. Dissecting and cross-mapping into a new game

**Valuable designs to lift:**

1. **The component-as-decorator retained tree.** One node, a stack of behaviours, symmetric pre/post hooks, and two-pass min/max/greed layout. It is a very small core (`Widget.cpp` + `List.cpp` + `Stack.cpp` ≈ 330 lines) that composes well (`Expand(Padding(CaptureMouse(Custom X)))`). It maps cleanly onto ECS-style UI or a modern retained framework.
2. **Keyed `Dynamic` reconciliation + `Rebuild`.** React-like regeneration of children from game state with hash keys. It is a good fit for overview tables, target lists and logs.
3. **Message bubbling with request/response messages** (`SendUp` commands, `GetLabel`/`GetObject` queries, `AddWidget` to the root window host, `TabSelect` group exclusivity). It is simple and decoupled. Copy the idea, and add typed events plus a real focus/keyboard model.
4. **Focus-channel arbitration** (topmost-deepest wins per Key/Mouse/Scroll channel, with recursive queries). It is simple and robust for overlapping HUD panels.
5. **Layer + compositor + projected cursor**: render a UI subtree offscreen and composite it with a stylised shader onto any mesh, with correct hit-testing. Good for diegetic or holographic cockpit UI.
6. **Procedural vector glyph and icon system** (SDF-ish quads, unit-space icons, HDR additive glow). It is resolution-independent and tiny, and the art direction comes almost entirely from ~18 small shaders plus `Colors.lts`.
7. **HUD design**: centre reticle with speed/integrity arcs, target direction arrows and lead markers; edge-anchored, movable/resizable panels (B mode); click-through from mini widgets (minimap → map, mini-scanner → scanner, badges → Show Info); radial RMB menus on world brackets; a Browser-style Show-Info with breadcrumbs and linked objects. All of this is directly reusable as **design reference** for an EVE-like game.
8. **Market screen flow**: category tabs with counts, search, a best bid/ask table, a selection panel, and a modal with a quantity slider that walks the order book. A good, compact reference implementation.

**Portability:**

| Part | Portability |
|---|---|
| Widget core (C++) | High. Small, but tied to LTE types (`Reference`, `Vector`, `Data`, `AutoClass` macros) and the LTSL bridge. A rewrite is ~1 day; it is not a direct copy. |
| WidgetRenderer / glyph shaders | Medium. The GLSL-like `.jsl` shaders and the vertex formats are easy to port. The batching code depends on the LTE Renderer. |
| LTSL screens | Low as code (a custom language) and high as *specifications*. Each screen file reads like a declarative layout plus behaviour, and is easy to transliterate to Lua/C#/GDScript/TS. |

**Replace vs keep:**

- **Dear ImGui.** Best for dev tools (DevPanel, ModelEditor, inspectors). It is a poor fit for the stylised HUD/hologram look and for the retained, message-driven game screens. Recommended only for tooling.
- **RmlUi / Noesis / Coherent / web-tech UI.** They give tables, text input, scrolling, styling and data binding for free, which addresses most of the framework gaps here (tables, focus, text, drag-drop). The glow/hologram look is reproducible with their render interfaces plus a post-composite. A good fit for EVE-style window-heavy UI (market, fitting, industry, overview tables).
- **Engine UI** (Godot Control nodes / Unity UI Toolkit / Unreal UMG). Godot's Control + container model is almost the same model as this one: min size, size flags expand/fill/stretch ratio ≈ greed, margin/anchor ≈ Align, signals ≈ messages. Porting the LTSL screens to Godot would be a near-mechanical translation.
- **Recommendation for a new game.** Keep the **design language and the screen specifications** (HUD layout, reticle, radial menus, Show-Info/Browser, market flow, glyph icon set, colours/fonts/sounds). Reimplement them on a mature UI library or engine UI. Optionally port the glyph shaders and the Layer/compositor trick for the in-space HUD. Do not carry the C++ framework forward unless the new game also stays on LTE/LTSL.
