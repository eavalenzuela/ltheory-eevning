# 04 — Game World Model (Objects, Items, Universe, Economy, Players)

Scope: `src/liblt/Game/Object/`, `src/liblt/Game/Item/`, `src/liblt/Game/ItemProperty/`, the world-model files at the top of `src/liblt/Game/`, `src/liblt/Game/ScriptAPI/`, and `resource/gamedata/`.
Neighbouring areas are only described where the world model depends on them: components (`src/liblt/Component`), tasks (`Game/Task`), attributes (`Game/Attribute`), and the LTSL scripts that the C++ calls back into (`resource/script/Object`, `resource/script/Item`).

How this was written: by reading the code. Nothing was built or run. Where I am inferring rather than reading, I say so ("appears", "probably", "unverified").

---

## 1. Overview

The world model is a **component-mixin object graph** plus a **procedural item-type system**:

* Every in-world thing is an `ObjectT` (refcounted, `Object = Reference<ObjectT>`). There are 43 `ObjectType` enum values (`OBJECT_X` in `Game/Common.h`). Each concrete type is built from a compile-time stack of `Component_X<...>` templates (45 component kinds, `COMPONENT_X`). There is no runtime ECS: a component is a field plus virtual overrides that the template adds.
* Every "kind of thing" (ship hull, weapon, ore, station design, planet...) is an `ItemT` (`Item = Reference<ItemT>`), with 24 `ItemType` values (`ITEM_X`). Item types are **generated from `(value, seed, a few float multipliers)`** by `Item_XxxType(...)` functions. An object points at its item through the `Supertyped` component, and `Item::Instantiate()` creates the object.
* The universe is generated from a seed: `Object_Universe(seed, depth)` → `Object_Region` (recursive) → `Object_System`. The C++ then calls the LTSL function `Object/System:Init`, which puts the planet, colonies, belt, asteroid zones, stations, market stock, pirates, warp rails and two AI "players" into the system.
* The economy is a real **order-book market** on each station (`Component/Market`). AI players (`Player_AI` + `Task_Play`) run "projects": they find profitable task chains such as Mine → Sell and assign their ships to them. This is what prints `Add Project Mine -> Sell X ...`.
* The human player is a `Player_Human` that pilots a ship. Flight, combat (pulse weapons) and mining (transfer-unit beam) work. Remote trading through the station market UI works. Warp-rail travel works. **There is no player-facing upgrade/fitting, cargo-transfer or docking UI, and no save/load.**

Unit conventions (`Game/Constants.h`): 1 distance unit = 1 km (design intent; in practice positions are in arbitrary large units), mass in kg, value in "RU" (resource units ≈ energy). Positions are `V3T<double>` (`Position`, `DistanceT = double` in `LTE/Common.h:59`). Time is `int64` quanta at `kTimeScale = 1000` per second.

## 2. Architecture

### 2.1 Object model

```
RefCounted
 └─ ObjectT  (Game/Object.h)            id, parent, container, children (intrusive list), deleted
     └─ ObjectWrapperTail<ObjectType_X> GetType()
         └─ Component_A< Component_B< ... >>   (each adds a ComponentX field + overrides)
             └─ concrete struct (Ship, Station, Planet, ...)  usually AutoClassDerived(..)+POOLED_TYPE
```

**Base class `ObjectT`** (`Game/Object.h`, 543 lines) is a "fat interface". It has about 150 virtual methods, grouped by the component that would implement them: Account (credits), Asset (owner), Assets, Attachable, Cargo (`AddItem/GetItemCount`), Container (`AddInterior`), Dockable, Integrity (health), Market (`AddMarketAsk/Bid`), MissionBoard, Motion (`ApplyForce`), Nameable, Sockets (`Plug`), Storage (`GetStorageLocker`), Tasks (`PushTask`), and others. Most defaults are `NOT_IMPLEMENTED` or return 0. A component mixin overrides the relevant subset. Calling the wrong method on an object type is a silent no-op, or `NOT_IMPLEMENTED` at runtime.

**Component access**: `Get##X()` returns `nullptr` unless the mixin is present, and `HasComponent(type)` is generated by X-macro. So "does this object have a market?" is `obj->GetMarket() != nullptr`, and LTSL sees it as `obj.HasComponentMarket` (`ScriptAPI/ObjectComponents.cpp`).

**Mixin mechanics** (`Component/Common.h: AutoComponent(x)`) generate `template<class BaseT> struct Component_x : BaseT { ComponentX x; Get##x(){return &x;} FIELDS{...} }`. Each mixin chains `OnUpdate`, `SetSupertype`, `GetCapability`, `GetValue` and so on to `BaseT`. Field reflection (`FIELDS`/`MAPFIELD`) runs through the whole stack. That means every object is in principle introspectable/serialisable, but no save system uses it (see §6).

**Two hierarchies at once**:

| Relation | Fields | Used for | API |
|---|---|---|---|
| **Parent/child** (attachment) | `parent`, `children`, `nextSibling` | Sub-parts: thrusters, turrets, weapons, generators plugged into a ship; a colony attached to a planet; a player "inside" a ship | `AddChild`, `Attach(child, transform)`, `GetRoot()` (walks up until an object with `Asset` component) |
| **Container/interior** (spatial) | `container`, `ComponentInterior.objects` | "Is located in": systems contain stations/ships/asteroids; stations/colonies contain docked ships; regions contain systems | `AddInterior`, `GetContainer()`, `GetSystem()`, `GetRegion()`, `GetUniverse()`, `Object_GetInteriorObjects(o[, type])` |

**Update loop**: `ObjectT::Update(state)` calls `OnUpdate`, then recurses into `children` and drops deleted ones. `Component_Interior::OnUpdate` → `ComponentInterior::Run` updates the interior objects. In practice **only the system the camera/player is in is ticked**: `App/ltheory.lts` calls `container.Update dt` on the player's container. Other systems and regions are frozen. `Pilotable.Run` calls `pilot->Update(state)`, so a `Player` (also an `ObjectT`) and its `Task_Play` brain run **only while the ship it pilots is being updated**. `Task_LOD` exists to simulate tasks abstractly off-screen but is never used.

**Messages**: `Send(T)` wraps the value in a `Data` and calls `OnMessage`. `Broadcast` sends to self, children and interior. Messages are plain `AutoClass` structs (`Game/Messages.h`), checked with `m.type == Type_Get<MessageX>()`:

| Message | Receiver(s) | Effect |
|---|---|---|
| `MessageThrustLinear/Angular`, `MessageCruise` | Thruster | Sets thrust, torque, cruise (100× power request) |
| `MessageBoost` | PowerGenerator | Discharges capacitor for extra output |
| `MessageFire`, `MessageTargetPosition`, `MessageTargetObject`, `MessageReload` | Weapon, TransferUnit, Turret, DroneBay | Fire / aim |
| `MessageLaunch` | DroneBay | Fires a `Payload` (prospecting drone) |
| `MessageLink` / `MessageUnlink` | WarpNode | Joins nodes into a rail network (shared controller) |
| `MessageStartUsing` / `MessageStopUsing` | WarpNode | Enter/leave a warp rail as a passenger |
| `MessageWaypoint`, `MessageEjected` | Passenger ship | Rail progress notifications (no C++ receiver found; scripts may listen) |
| `MessageGetColor`, `MessageCollectStars` | Star | Star colour query (used for nebula/lighting) |

LTSL defines more message types (e.g. `MessageGatherWidgets`, `MessageFireworks`, `MessageInfo`, `MessageTrade`). Those are UI-level and live in the scripts. `MessageInfo` is not a C++ type.

**Sockets / plugging** (`Game/Socket.h`, `Component/Sockets`): an item type with sockets (`ShipType`, `TurretType`) exposes an `Array<Socket>{transform, SocketType, JointType}`. `SocketType` is one of **Generator, Interior, Thruster, Turret**. `obj->Plug(item)` finds the first empty socket whose type equals `item->GetSocketType()`, calls `item->Instantiate(self)` and attaches the result as a child. Plugging is **free**: it does not consume an item from cargo and there is no fitting budget. `WeaponType`/`TransferUnitType::Instantiate` return a `Turret` with the weapon/beam plugged into the turret's single socket.

| Item type | SocketType | Notes |
|---|---|---|
| ThrusterType | Thruster | ShipType fills all thruster sockets with `standardThruster` on instantiate |
| PowerGeneratorType, ScannerType, ShieldType | Generator | The scanner uses a Generator socket because there is no scanner socket type |
| WeaponType, TransferUnitType | Turret (via a Turret object) | Weapons and mining beams compete for the same hardpoints, like EVE high slots |
| TechLabType, ProductionLabType, DroneBayType | Interior | Small ships get **0** interior sockets (`2*int(log(scale)/log(10))`) |

**Power**: there is no static CPU/powergrid. `PowerGenerator` gathers `Pluggable.powerRequest × priority` from every plugged module each frame, then sets each module's `powerIn` to `request × (output/total)`, smoothed. Modules use `GetPowerFraction()` to scale their output: thrust, beam activity, shield recharge. Weapons never set a power request, so they are effectively free.

**Capabilities** (`Game/Capability.h`): a float vector over `Attack, Defense, Detection, Motion, Power, Production, Research, Storage, Transference`. Items declare a capability. `Sockets` and `Assets` sum capabilities over children/assets. So `ship->GetCapability().Storage` is cargo capacity, `.Motion` is total thrust, and so on. Tasks use capability vectors for rate and scale factors.

**Health/damage**: `ObjectT::ApplyDamage` damages Shield sockets first, then `Integrity`. When integrity reaches 0, `OnDeath()` runs, `Explodable` spawns VFX, and `Asset.Run` logs the loss and removes the object from its owner's assets. **Dead objects are not deleted** (ships appear to remain as hulks; unverified at runtime). `Event_Damage` (Game/Event) also tells the victim's owner (`OnAttacked` → opinion −1) and gives the attacker a `DataDamaged` item. That item is "evidence" a mission could pay for (§2.4).

**Signatures/sensors**: `Signature{amplitude, frequency(log Hz), variance, power}`. Overrides exist on Star, Ship, AsteroidRich, Colony and Wormhole. `Object_GetScannerOutput(scanner, bands)` sums the spectra of every object in the container, weighted by angle and distance. `Object_GetSignature` returns one object's spectrum. These drive the scanner HUD widgets (`Widget/Scanner.lts`, `HUD/Miniscanner.lts`, `Object/Overview.lts`). The **info/fog-of-war** path (`Scanner::OnUpdate` → `ComponentInfo::Add(InfoLevel_Location)`) is disabled by an early `return` ("CRITICAL : Disabled scanners"). Only `Asset.Run` writes Info (owners always see their own assets).

### 2.2 Item model (types vs. instances)

```
ItemT (Game/Item.h)  id; virtual Get<Prop>()/Has<Prop>() for 22 ITEMPROPERTY_X props
 └─ ItemWrapper<ItemType_X>       GetType()
     └─ Attribute_A< Attribute_B< ... >>   (Game/Attribute/*.h: each adds a field + Get/Has override)
         └─ concrete type struct (ShipType, WeaponType, ...) + Instantiate()
```

* **Items are types, not stacks.** An item is shared by every instance. Quantities live in `ComponentCargo` (`Map<Item, Quantity>`), market orders (`Order{item, volume, price}`) and `ItemQuantity`.
* **Identity is per generated instance, not per parameters.** `GetHash()` defaults to `id % HASHT_MAX`, and `id` is a global counter. Calling `Item_WeaponType(46)` twice gives two different, incompatible items with separate market books and cargo stacks. Callers have to cache. `Task_Play` caches ship types by value bucket. `Item_TurretType` is a singleton. Nothing else caches.
* **Generic properties** (`ITEMPROPERTY_X`): Capability, Color, Description, Hash, Icon, Integrity, Mass, Metatype, Name, Object, PowerDrain, Range, Rate, Renderable, Scale, Seed, Speed, StorageType, Task, Traits, Type, Value. Each one is reflected as an `ItemProperty_<Name>` object (`Game/ItemProperty.h`). Missions use these to constrain items (§2.4). `ItemProperty_Owner` (`ItemProperty/Owner.cpp`) is the only derived property: the owner of the object an item refers to.
* **StorageType** routes items: `Cargo` (normal), `Database` (DataDamaged/DataDestroyed logs, stored in `Component/Database`), `CrewQuarters` (unused).
* **Metatype = generator arguments.** Generated types store their `Item_X_Args` struct (`Attribute_Metatype`, `DeclareFunctionArgBind`). This lets `Blueprint` re-run the generator with mutated parameters (§2.4).

**Procedural parameterisation.** Every generated type is `f(value, seed, multipliers...)` through the conversion curves in `Game/Constants.h`:

| Curve | Formula |
|---|---|
| ValueToMass(v, compactness) | v / compactness / 10 |
| ValueToCapacity(v, cap) | ValueToMass(v·cap) / 10 |
| ValueToIntegrity(v, str) | ValueToMass(v·str) / 10 |
| ValueToOutput(v, rate) | v · rate |
| ValueToPowerDrain(v, eff) | v / eff |
| MassToScale(m) | sqrt(m / 1000) |
| RangeRatio(x) / SpeedRatio(x) | 1000·x / 1000·x^1.5 |

| Item type (file) | Generator signature | What is generated | Status |

### 2.3 Universe generation pipeline

```
App/ltheory.lts: Object_Universe(39, depth=0)
  Universe (C++ Game/Universe.cpp)
    ├─ ore RNG (fixed seed 190!): currencyBasis OreType(1,·) + 8 OreTypes value=10*(5*Exp+1); Resources weight = 1/value
    ├─ colonyTypes = { "Farming" ColonyType(Task_Spawn(ore0)) }       (unused afterwards)
    └─ 1 Region (level = depth, pos random, radius 100, resources = half the ores randomly weighted)
         Region (Object/Region.cpp)  name = Grammar "$system"
           childCount = 1 + int(5*Exp)  (kMaxChildren is hard-coded to 1)
           circle-pack children inside radius
           level>0 → child Region(level-1, jittered resources)
           level==0 → Object_System(pos, seed) + ScriptFunction "Object/System:Init"(system)
           connect children: 2 rounds of randomized MST → Object_Wormholes(nearest systems) (pair at ±400000)
             System (Object/System.cpp): Star at 6e7 units, nebula cubemap (disk-cached), starfield, DustFlecks
             Object/System:Init (resource/script/Object/System.lts):
               name = Grammar "$system"
               1 Planet (Item_PlanetType rng+8), named "Melian Prime" (hard-coded)
                 1–3 Colony on planet surface (ColonyType w/ Task_Spawn(WeaponType 53), random Traits)
                   each Colony gets a Player_AI "Governor" with 1,000,000 credits
                 orbital belt Zone (torus SDF, 1 static asteroid)
                 4 radial WarpNode rails around planet
               2 Zones (sphere SDF, 96 rich asteroids each)
                 each: Station (StationType 1e9) + Player_AI "Manager" (1e6 credits)
                       32 random sell orders from commonItems (32 WeaponTypes, DroneBay, ProductionLab, TechLab, TransferUnit)
                       2 "Patrol Unit" ships (value 1e7) vs 3 pirates each, all at 1e9 health, Task_Destroy each other
               WarpNode rails from POI 0 (planet) to every other POI (zones)
               2 AI players: Player_AI + boss ShipType(1e8), 1,500,000 credits, 4 transfer units, weapons, Task_Play
```

* Naming: `LTE/Grammar.cpp` loads **only** `resource/gamedata/grammar/default.txt`. This is a weighted context-free grammar: rules `name\n weight|token|$rule...`, plus `#tag` support. Rules used by the world model: `$system`, `$station`, `$station_midfix`, `$oretype`, `$weapon` (tagged with the weapon class), `$faction` (AI player names in `Task_Play`). LTSL exposes `Grammar_Get "$rule" rng`.
* Determinism: generation is seeded throughout (RNG_MTG). The exceptions are `Rand()`/`rand()` used in physics, combat and `Blueprint` mutation, and the static counter in `Task_Play::GetShipType`.
* Scale actually produced by `ltheory.lts`: depth 0 means 1 region with about 1–6 systems. Each system has 1 planet, 1–3 colonies, 2 stations, ~193 rich asteroids, 4 patrols, 12 pirates and 2 AI factions. Only the starting system is simulated.
* The C++ pipeline **depends on LTSL scripts at generation time**: `Object/System:Init`, `Object/Ship:Init`, `Object/Colony:Init`, `Object/WarpNode:Init`, `Object/Thruster:Init`, `Item/ShipType/Generate:Main`, `Item/StationType/Generate:Main`, `Item/*Type:Generate`, `Icons:*`. You cannot generate a universe without the script runtime.

### 2.4 Economy

```
           ┌─────────────── System (Component_Economy, recomputed EVERY frame) ───────────────┐
           │ nodes  = objects with Market (stations, colonies)                                  │
           │ items  = all items seen in cargo/markets/zone resources                            │
           │ tasks  = Task_Mine(zone), Task_Pirate(zone) per resource zone                       │
           │          Task_Transport(a,b,item) for every market pair × item (both directions)    │
           │          Task_Produce(chip) per AssemblyChip, Task_Mint/Task_Research per Blueprint │
           └─────────────────────────────────────────────────────────────────────────────────────┘
Player_AI ──Task_Play──► FindProject(): random economy task; bind unbound inputs/outputs by wrapping
                          in Task_Buy(node,..)/Task_Sell(node,..)  → "Mine -> Sell Kygen -> Sell ..."
                       ► ConsiderProject(): Project_Create; gross = outputValue - inputValue + task value;
                          keep if gross ≥ 1 and < kMaxProjects(=1)  → dbg "Add Project ..."
                       ► AllocateFreeAsset(): Project_Allocate(ship) → ship.PushTask(project.task)
                       ► ManageProject(): Task_Manage (metaprojects Develop/Expand/Monopolize/Secure; only
                          Monopolize does anything: posts a "Damage the Enemy" Mission)
                       ► SpawnNew(): buys ShipTypes (value ~ credits·Rand^8, cached per power of 10),
                          plugs transfer units + weapons, up to 16 assets
Station (Component_Market): per-item order book (asks/bids), matched every frame at mid price,
          escrow: AddBid takes credits up front; AddAsk takes items out of the owner's storage locker;
          fills go into the buyer's locker (Pod) at that station; 27-level EMA price/volume history
```

| Concept | Where | Notes |
|---|---|---|
| Credits | `Component/Account` (Player, Colony) | `int64` quantities. No global money supply control |
| Ownership | `Component/Asset` (owner on object), `Component/Assets` (list on player) | `GetRoot()` stops at the first object with `Asset`. `GetOwner()` walks up parents |
| Storage lockers | `Component/Storage` | One `Pod` per owner per station. This is where market goods live (EVE-like personal hangar) |
| Orders | `Game/Order.*` | `{owner, item, volume, price, filledVolume, filledTotal, node}`. Owner gets a copy in `Component/Orders` |
| Markets | `Component/Market.*` | Regional books per station. No cross-station or regional aggregation. Trade timestamps use `Universe_Age()`, which is always 0 (§6) |
| Projects | `Game/Project.*` | A task chain + allocated assets + metrics + wallet with revenue-feedback (90% of sales recycled into the project wallet). Places buy orders for inputs and sell orders for whatever is in the owner's locker |

### 2.5 Player model

```
PlayerT (Game/Player.h) : ObjectT   [abstract]   piloting, stats, IsHuman(), Pilot(), Unpilot(), OnAttacked()
  └─ PlayerImpl (Player.cpp)  isHuman flag
       Player_AI(traits)  — gets Task_Play pushed by System.lts; governors/managers get none (passive owners)
       Player_Human()     — driven by LTSL widgets (Widget/Handling.lts, HUD)
```

* `Pilot(ship)`: sets `ship.Pilotable.pilot = player`, `player.piloting = ship`, `player.container = ship` (the player "lives" in the ship). The ship's update ticks the player.
* Human control path: keyboard/mouse in LTSL (`Widget/Handling.lts`: WASD/QE/Space/Tab/mouse) → MotionControl/Thruster messages; `target.Broadcast MessageFire` fires all weapons/beams. HUD world-object menu (`Widget/HUD/WorldObject.lts`): Target, Trade (opens market), Information, `[DEV] Jump To` (teleport), Fireworks. In `ltheory.lts`, Y/U send `MessageStartUsing/StopUsing` to the current target (warp-node ride). Holding H runs time 20× faster.
* Assets: `player.AddAsset obj` sets the owner. AI players spawn and own fleets. The human starts with one ship and 10,000 credits.
* Death: `Pilotable.Run` clears the pilot if the ship dies ("TODO: What if player dies?"). No respawn, clone or insurance.

## 5. Script exposure (LTSL)

There are two binding mechanisms, and both register into `GetFunctionMap()` (`LTE/Function.cpp`) so the LTSL compiler can resolve them by name:

1. **`DefineFunction(Name)`** on a `DeclareFunction(...)` prototype. This covers every factory: `Object_Universe/Region/System/Planet/Station/Ship/Colony/Zone/Asteroid/AsteroidRich/WarpNode/WarpRail/Wormhole/Custom/Pod/Payload/Missile/Explosion/Weapon/Turret/Scanner/Shield/PowerGenerator/TechLab/ProductionLab/TransferUnit/SoundEmitter/Star/DustFlecks/Light/GetZone/AddHistory`, `Item_ShipType/StationType/PlanetType/WeaponType/ThrusterType/PowerGeneratorType/ScannerType/ShieldType/TransferUnitType/TurretType/TechLabType/ProductionLabType/DroneBayType/Drone*Type/OreType/ColonyType/AssemblyChip/Worker_*`, `Player_AI/Player_Human`, `Order_Create`, `Mission_Create`, `Project_Create/Allocate/Deallocate`, all 20 `Task_*`. (`Object_Thruster`, `Object_Static/Dynamic/Pulse/Rail/Trail`, `Item_Blueprint*`, `Item_Commodity` and `Item_Data_*` are plain `LT_API` functions and are **not** script-callable.)
2. **`FreeFunction` / `VoidFreeFunction` + `FunctionAlias`** for methods (alias allows `obj.Method` syntax):

## 8. Assessment for the two goals

### 8a. Shortest path to a minimal playable loop (fly → mine → sell → upgrade)

What already works for a human: flying, targeting, shooting (pulse), mining with a transfer unit (the ship must have one plugged; `ltheory.lts` has it commented out), cargo, viewing station markets remotely, placing buy/sell orders, credits, warp rails, and the scanner HUD.

| Step | Gap | Suggested minimal fix (mostly LTSL) |
|---|---|---|
| 1. Mining ship | `ltheory.lts` plugs only weapons | Uncomment `ship.Plug (Item_TransferUnitType 1 1 1 1 1 1)`. Consider a larger starting `Item_ShipType` value so there is useful cargo (20000 → capacity ≈ 120 mass units) |
| 2. Dock | No player dock action | Add an HUD menu option "Dock" on objects with `HasComponentDockable`: `player.GetPiloting.PushTask (Task_Dock object)`. For undock, push `Task_Goto` outward, or bind a C++ `Object_Undock`. **Remember the camera/update container changes to the station when docked** (`ltheory.lts` updates `player.GetPiloting.GetContainer`, so the station's interior is ticked, but the system outside may stop being updated) |
| 3. Sell ore | Market asks require items in the station **locker**; mined ore is in ship cargo | Add "Deposit cargo" / "Withdraw" buttons in `Widget/Market/MidPanel.lts`: iterate `ship.GetCargo`, `locker.AddItem item n`, `ship.RemoveItem item n` (all bound). Ore has no bids by default. The only bidders are AI projects buying their task inputs (e.g. a `Task_Transport` of an ore that some AI has already listed), and with 2 AI players × 1 project per system that is rare. Seed station bids in `System.lts` (`station.AddMarketBuyOrder manager ore …` for each `Resources` ore) |
| 4. Buy modules | Station stock exists (32 random sell orders of weapons, labs, transfer units) | Works already; goods land in your locker |
| 5. Upgrade/fit | No UI. `Plug` is free and doesn't consume items | Add a fitting widget: for each item in the locker with a socket type, `ship.Plug item` then `locker.RemoveItem item 1`. Add a C++ `Object_Unplug(slot)` binding (ComponentSockets::Unplug exists) to swap modules. Optionally enforce a power budget using `Capability.Power` vs sum of `PowerDrain` |
| 6. Ship purchase | None for the player | Sell `Item_ShipType` items in station markets (`Item_Instantiate` gives the ship). Or copy `Task_Play::SpawnNew` logic into an LTSL "shipyard" |
| 7. Danger/stakes | Pirates are decorative (1e9 HP, fight each other) | Lower pirate health. Push `Task_Destroy player.GetPiloting` on some pirates. Add a respawn on death |
| 8. Persistence | None | Defer. Re-generating from the seed plus serialising the player's ship/credits/lockers is the cheapest first step |
| Perf | Economy rebuild every frame | Throttle `ComponentEconomy::Run` to every N seconds (C++, one line) |

Estimate: steps 1–5 are a few hundred lines of LTSL plus 1–2 tiny C++ bindings, all on existing systems. Missions, industry and inter-system play need real C++ work: a mission turn-in path, blueprint seeding, the `GetOutputs` fix, and simulation of non-current systems.
